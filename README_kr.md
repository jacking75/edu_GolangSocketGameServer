# golang_socketGameServer_codelab

[English version](README.md)

- golang을 이용하여 실시간 통신 게임 서버 만들기 실습.  
- 각 서버의 원본 코드를 하나씩 따라서 코딩하면서 서버 만드는 방법을 배운다.
    - 코딩하면서 해당 코드의 구현 방법과 이유를 설명 듣는다.
  
**버그가 있을 수 있습니다**. 버그 잡아서 수정하는 것도 학습 중 일부라고 생각해 주세요^^;.  
  
  
## 목적 
- golang으로 소켓 통신용 서버를 만들 수 있는 기술과 경험을 쌓는 것이 목표이다.
- golang으로 소켓 통신용 서버를 만든 경험이 없는(있더라도 작은) 사람을 대상으로 한다.  
- golang의 socket API를 사용하지 않고, 센트럴서버팀에서 만든 goHiperNet(golang 네트워크 라이브러리)의 짝퉁(?)을 사용한다.
    - 이 라이브러리는 goHiperNet과 API만 같고, 내부 구현은 완전 다르다. 
	- 학습용으로 충분히 사용할 수 있다.
	- golang의 socket API를 사용하여 밑바닥부터 개발하는 방법을 배우고 싶다면 별도 요청을 바람.
- 실습은 단계 별로 진행하고, 각 단계 별로 소요 시간은 다르다.
    - 시간이 많이 필요한 경우라도 1번에 최대 3시간을 넘지 않는다.
	- 한번에 너무 많이 나가면 뒤에 복습이 어려워지기 때문이다.
- 왜 "게임 서버"를 예제로 쓰는가?
    - 게임 서버는 "접속을 유지한 채로 여러 클라이언트가 실시간으로 상태를 주고받는" 전형적인 소켓 프로그래밍 사례다.
    - 채팅방(room), 로그인, 동시 접속자 여러 명이 얽히는 상황을 다루다 보면, 웹 API 서버(요청 하나 받고 응답 하나 주고 끝)에서는 잘 겪지 않는 문제들(동시성, 상태 관리, 순서 보장)을 자연스럽게 마주치게 된다.
   
   
## 준비
- 1인 1 노트북(Windows or OSX)
- 최신 버전의 golang SDK
- 최신 버전의 GoLand  
- 기본 golang의 문법 학습
    - 코딩은 한번도 해본적인 없는 경우도 괜찮음.  
- (선택) 클라이언트로 접속 테스트를 해보고 싶다면: Windows + Visual Studio 2022 이상(.NET 8.0 SDK 포함)
    - 클라이언트 없이 서버 코드만 읽고 빌드해 보는 것만으로도 실습은 진행할 수 있다.
    - 클라이언트는 C#으로 작성되어 있어서 macOS에서는 실행하기 어렵다(Windows 전용 WinForms 앱). macOS 사용자는 서버 코드 학습 위주로 진행하고, 접속 테스트가 꼭 필요하면 Windows PC를 하나 빌리거나 나중에 직접 텍스트/GUI 클라이언트를 만들어봐도 좋은 연습이 된다.
     
  	 
## 미리 알아두면 좋은 개념

이 저장소의 코드를 처음 읽을 때 자주 나오는 용어를 미리 정리해 둔다. 이미 익숙하다면 건너뛰어도 된다.

- **소켓(Socket) / TCP 접속**: 클라이언트와 서버가 네트워크로 데이터를 주고받기 위해 맺는 "연결"이다. 한번 연결되면(접속하기), 끊기 전까지(접속 끊기) 그 연결을 통해 계속 데이터를 주고받을 수 있다. 이 저장소의 서버들은 전부 TCP를 사용한다.
- **패킷(Packet)**: 클라이언트와 서버가 주고받는 데이터 한 덩어리. "로그인 해줘", "채팅 보낼게" 같은 요청 하나하나가 패킷 하나에 해당한다. 자세한 형식은 [패킷 헤더](#패킷-헤더) 절 참고.
- **패킷ID**: 이 패킷이 무슨 종류인지(로그인 요청인지, 채팅 요청인지 등)를 나타내는 숫자. 각 서버의 `protocol/packetID.go` 파일에 전체 목록이 정의되어 있다.
- **직렬화(Serialization) / 인코딩·디코딩**: 프로그램 안의 구조체(예: `LoginReqPacket{UserID: "abc", PassWD: "123"}`)를 네트워크로 보낼 수 있는 순수한 바이트 배열로 바꾸는 것(인코딩), 그리고 반대로 받은 바이트 배열을 다시 구조체로 되돌리는 것(디코딩)을 말한다. `chatServer`/`baccaratServer` 계열은 직접 만든 방식으로, `chatServer_msgpack`은 msgpack이라는 표준 포맷으로 이 작업을 한다.
- **고루틴(Goroutine)**: Go 언어가 제공하는 아주 가벼운 "동시 실행 흐름"이다. 다른 언어의 스레드와 비슷하지만 훨씬 가볍게 수만 개까지도 만들 수 있다. `chatServer`는 모든 패킷 처리를 고루틴 1개에서 순서대로 처리하고, `chatServer2`는 여러 고루틴에 나눠서 동시에 처리한다 — 이 차이가 두 서버의 가장 큰 구조적 차이다.
- **세션(Session)**: 서버에 접속한 클라이언트 한 명 한 명을 서버 내부에서 관리하기 위한 단위. 접속하면 세션이 하나 만들어지고, 로그인/방 입장 같은 상태가 이 세션에 기록된다. 코드에서는 `connectedSessions` 패키지가 이 역할을 한다.
- **방(Room)**: 채팅이나 게임이 실제로 이루어지는 논리적인 공간. 클라이언트는 로그인한 뒤 특정 번호의 방에 "입장"해야 그 방에 있는 다른 사람과 채팅하거나 게임을 할 수 있다. 코드에서는 `roomPkg` 패키지가 이 역할을 한다.
- **리틀 엔디안(Little Endian)**: 이 저장소의 프로토콜이 숫자를 바이트로 표현할 때 쓰는 방식이다. 예를 들어 정수 700을 2바이트로 쓸 때, 큰 자리 바이트가 아니라 작은 자리 바이트를 먼저 쓴다. [패킷 헤더](#패킷-헤더) 절의 예시를 참고하면 이해가 빠르다.

이 저장소는 크게 "① golang으로 만든 서버들", "② 서버가 공통으로 쓰는 가짜 네트워크 라이브러리", "③ 서버에 접속해서 테스트해 볼 수 있는 C# 클라이언트"로 이루어져 있다.

| 디렉토리 | 무엇인가 | 언어 |
|---|---|---|
| `gohipernetFake` | 모든 서버가 공통으로 사용하는 네트워크 라이브러리(짝퉁 goHiperNet). 소켓을 직접 다루는 코드는 전부 여기 있다. | Go |
| `echoServer` | 가장 단순한 서버. 받은 데이터를 그대로 돌려준다(에코). 실습의 첫 단계. | Go |
| `chatServer` | 방(room) 개념이 있는 채팅 서버. 패킷 처리를 고루틴 1개에서만 한다. | Go |
| `chatServer2` | `chatServer`를 여러 고루틴으로 병렬 처리하도록 발전시킨 버전. **현재 저장소 상태로는 빌드가 되지 않는다**(아래 [chatServer2](#chatserver2) 절 참고). | Go |
| `chatServer_msgpack` | `chatServer`와 거의 같지만, 패킷 데이터를 JSON 비슷한 바이너리 포맷인 msgpack으로 주고받는다. | Go |
| `baccaratServer` | `chatServer` 위에 바카라 카드 게임 로직을 얹은 서버. | Go |
| `csharp_test_client` | `chatServer` / `chatServer2` / `baccaratServer`(방 입장, 채팅, 릴레이 기능만) 접속 테스트용 Windows GUI 클라이언트. | C# (.NET 8, WinForms) |
| `csharp_test_client_msgpack` | `chatServer_msgpack` 전용 접속 테스트 클라이언트. | C# (.NET 8, WinForms) |
| `bin` | 빌드된 서버 `.exe`를 실행할 때 쓰는 예시 배치 파일(`run_xxx.bat`)과 로그 설정 파일이 들어있다. | - |
| `thirdparty/SimpleMsgPack.Net` | C# 클라이언트가 msgpack을 다루기 위해 가져다 쓰는 오픈소스 라이브러리(일부 코드 수정됨). | C# |
| `lib_opensource` | 참고용으로 담아 둔 다른 오픈소스 Go 네트워크 라이브러리 압축 파일들. 실습에는 사용하지 않는다. | - |

각 Go 서버 디렉토리(`echoServer`, `chatServer`, `chatServer2`, `chatServer_msgpack`, `baccaratServer`)는 **자기 자신만으로 완전히 독립된 Go 모듈**이다(각자 `go.mod`가 있다). 그래서 어느 폴더를 열어도 그 폴더 하나만 보면서 코드를 따라갈 수 있고, 서버 사이에 겹치는 코드(세션 관리, 방 관리 등)는 실습 목적상 폴더마다 그대로 복사되어 있다(공통 라이브러리로 뽑아내지 않았다). `gohipernetFake`만 예외로, 나머지 5개 서버가 전부 이 라이브러리를 `go.mod`의 `replace` 지시자로 상대 경로(`../gohipernetFake`)를 통해 가져다 쓴다.

### `chatServer` 계열(`chatServer`, `chatServer2`, `chatServer_msgpack`, `baccaratServer`) 서버 하나의 내부 구조

echoServer를 제외한 나머지 서버들은 전부 다음과 같은 공통 패턴으로 폴더가 나뉘어 있다. 어느 서버를 열어도 이 구조를 기준으로 코드를 찾아가면 된다.

| 폴더/파일 | 역할 |
|---|---|
| `main.go` | 프로그램 진입점. 커맨드라인 옵션(`-c_BindAddress` 등)을 읽고 서버를 시작한다. |
| `chatServer.go` / `baccaratServer.go` (서버 이름과 동일한 파일) | 서버를 초기화하고 `gohipernetFake`에 "이런 이벤트가 오면 이 함수를 불러줘" 하고 등록하는 코드. |
| `distributePacket.go` | 클라이언트에게서 패킷이 도착했을 때 가장 먼저 호출되는 곳. 패킷ID를 보고 로그인 처리인지, 방으로 보낼 패킷인지 등을 판단해서 나눠준다("배달부" 역할). |
| `connectedSessions/` | 접속한 클라이언트(세션) 하나하나의 상태(로그인 여부, 현재 있는 방 번호 등)를 관리하는 코드. |
| `protocol/` | 패킷 형식(구조체), 패킷ID 목록, 에러 코드 목록, 그리고 구조체 ↔ 바이트 변환(인코딩/디코딩) 코드가 들어있다. |
| `roomPkg/` | 방(room) 목록 관리와, 방 안에서 일어나는 일(입장, 퇴장, 채팅, 게임 등)을 처리하는 코드. 파일이 `room_Packet으로` 시작하면 "그 패킷을 받았을 때 방에서 무슨 일을 하는가"를 담당한다고 보면 된다. |

`baccaratServer`는 여기에 `roomPkg/Game.go`(카드 셔플, 배팅, 승패 판정 등 바카라 게임 규칙 자체)가 추가로 있다.

  
## 학습 순서

권장 순서는 다음과 같다. 각 단계는 이전 단계의 코드/개념을 이해하고 있다는 전제로 만들어져 있으니, 순서를 건너뛰지 않는 것이 좋다. 각 단계에서 "무엇을 눈여겨봐야 하는지"도 함께 적어 둔다.

1. **[준비](#준비)** 를 마치고, **[미리 알아두면 좋은 개념](#미리-알아두면-좋은-개념)** 과 **[패킷 헤더](#패킷-헤더)** 절을 한 번 읽어 이 저장소의 서버들이 어떤 형식으로 패킷을 주고받는지 감을 잡는다. 지금 전부 이해하지 못해도 괜찮다 — echoServer/chatServer 코드를 실제로 읽으면서 다시 돌아와 보면 훨씬 잘 이해된다.
2. **[설명 영상](#설명-영상)** 의 "실습 목적과 방법 설명" 영상을 본다.
3. **`echoServer`** — 가장 간단한 서버부터 시작한다. "Echo Server 만들기" 영상을 함께 본다.
    - 눈여겨볼 것: 서버가 소켓을 열고, 클라이언트 접속을 받고, 받은 데이터를 그대로 돌려주기까지의 최소한의 흐름. 파일이 `echoServer.go`, `main.go` 딱 두 개뿐이라 전체 그림을 파악하기 좋다.
4. **`chatServer`** — 방/로그인 개념이 있는 첫 번째 "진짜" 게임 서버 구조. "채팅 서버 코드 설명" 영상을 함께 본다. **이 서버를 제대로 이해하는 것이 이후 모든 단계의 전제조건이다.**
    - 읽는 순서 추천: `main.go`(시작) → `distributePacket.go`(패킷을 어떻게 나눠주는지) → `connectedSessions/session.go`(세션 하나가 어떤 상태를 갖는지) → `roomPkg/room.go`(방 하나가 어떤 상태를 갖는지) → `roomPkg/room_PacketEnter.go`(로그인한 유저가 방에 들어오는 과정) → `roomPkg/room_PacketChat.go`(채팅이 방 안의 다른 사람들에게 전달되는 과정).
    - 눈여겨볼 것: "로그인 → 방 입장 → 채팅"이라는 하나의 시나리오가 여러 파일에 걸쳐 어떻게 연결되어 있는지. 패킷 하나가 들어왔을 때 함수 호출이 어떤 순서로 이어지는지 손으로 따라가 보자.
5. 여기서부터는 목적에 따라 두 갈래로 나뉜다(순서는 상관없다).
    - **게임 로직에 관심이 있다면 → `baccaratServer`** (chatServer + 카드 게임 로직). `roomPkg/Game.go`부터 읽으면 된다.
    - **멀티 고루틴 동시성 처리에 관심이 있다면 → `chatServer2`** (chatServer를 여러 고루틴으로 병렬화). 다만 현재 코드는 빌드가 안 되는 상태이니 [해당 절](#chatserver2)을 먼저 읽어보길 권한다.
    - **직렬화 포맷에 관심이 있다면 → `chatServer_msgpack`** (chatServer + msgpack 직렬화). `chatServer`와 파일을 나란히 놓고 `protocol/packet.go`의 차이만 비교해 보면 빠르게 이해된다.
6. 각 단계를 하나 끝낼 때마다, 그 서버를 [직접 실행하고](#go-서버를-빌드하고-실행하는-방법) [클라이언트로 접속해서](#테스트-클라이언트-사용법) 방금 읽은 코드가 실제로 어떻게 동작하는지 눈으로 확인해 보자. 코드만 읽는 것보다 훨씬 오래 기억에 남는다.

  
## 패킷 헤더
패킷 헤더의 크기는 총 5바이트이고, 모든 패킷은 이 헤더로 시작한다.

| 필드 | 크기 | 의미 |
|---|---|---|
| 패킷의 총 크기 | 2바이트 | 헤더 5바이트 + 보디(body)를 합친 이 패킷 전체의 바이트 수 |
| 패킷ID | 2바이트 | 이 패킷이 무슨 종류인지(로그인 요청, 채팅 요청 등) |
| 패킷Type | 1바이트 | 0=일반, 그 외 값은 압축/암호화 등에 사용(이 저장소의 실습 코드에서는 사용하지 않음) |

숫자는 모두 **리틀 엔디안**(작은 자리 바이트가 앞에 온다)으로 기록한다.

### 예시로 직접 손으로 만들어보기

로그인 요청(`PACKET_ID_LOGIN_REQ`, 패킷ID = 701)을 보낸다고 해보자. `chatServer`의 로그인 요청 보디는 "UserID 16바이트 + 비밀번호 16바이트"로 고정 크기다(짧으면 뒷부분을 0으로 채운다). 그러면 패킷 전체 크기는 5(헤더) + 16 + 16 = **37바이트**가 된다.

이걸 바이트로 그려보면 다음과 같다(16진수, 왼쪽이 먼저 전송되는 바이트).

```
25 00   BD 02   00   [UserID 16바이트]   [비밀번호 16바이트]
└─┬──┘ └─┬──┘  └┬┘
  │      │      └ 패킷Type = 0
  │      └ 패킷ID = 701 (0x02BD, 리틀 엔디안이라 BD, 02 순서)
  └ 총 크기 = 37 (0x0025, 리틀 엔디안이라 25, 00 순서)
```

이 바이트들을 있는 그대로 TCP 소켓에 써서 보내면 서버가 그대로 읽고 해석한다 — 사람이 읽을 수 있는 텍스트가 아니라 이런 순수 바이너리이기 때문에, telnet 같은 텍스트 도구로는 이 서버들을 테스트할 수 없다(그래서 [테스트 클라이언트](#테스트-클라이언트-사용법)가 필요하다).

## Go 서버를 빌드하고 실행하는 방법

`echoServer`, `chatServer`, `chatServer_msgpack`, `baccaratServer` 4개는 모두 같은 방식으로 빌드/실행한다(`chatServer2`는 현재 빌드가 안 되므로 제외 — [아래 절](#chatserver2) 참고). 두 가지 방법이 있다.

### 방법 1) 터미널에서 바로 실행 (가장 간단함)

서버 디렉토리로 들어가서 `go run .` 뒤에 접속 주소/최대 접속자 수 등을 옵션(플래그)으로 넘겨서 실행한다. 예를 들어 `echoServer`는 다음과 같다.

```bash
cd echoServer
go run . -c_IsTcp4Addr=true -c_BindAddress=127.0.0.1:11021 -c_MaxSessionCount=200 -c_MaxPacketSize=1024
```

실행하면 아래처럼 로그가 출력되고, 그 상태로 접속을 기다린다(멈춘 게 아니라 정상이다. 종료하려면 `Ctrl+C`).

```
[ info ] tcpServerStart - Start
2026/08/27 23:53:28 Server Listen ...
```

각 플래그가 무슨 뜻인지는 다음과 같다.

| 플래그 | 의미 |
|---|---|
| `-c_IsTcp4Addr` | IPv4 주소를 쓸지 여부. 특별한 이유가 없으면 `true`로 둔다. |
| `-c_BindAddress` | 서버가 붙어서 접속을 기다릴 IP와 포트. `127.0.0.1`은 "내 컴퓨터 자기 자신"을 뜻한다. |
| `-c_MaxSessionCount` | 동시에 접속 가능한 최대 클라이언트 수. 이 개수만큼 세션 슬롯을 미리 확보해 둔다. |
| `-c_MaxPacketSize` | 패킷 하나가 가질 수 있는 최대 크기(바이트). |

> **주의**: `-c_MaxSessionCount`를 빼먹고 실행하면 기본값이 0이 되어, 서버는 켜지지만 **아무도 접속할 수 없다**(내부적으로 접속 가능한 세션 슬롯이 0개로 초기화되기 때문). 반드시 위 예시처럼 플래그를 함께 넘기자.

서버마다 넘겨야 하는 플래그가 조금씩 다른데, `bin` 디렉토리의 배치 파일에 서버별로 검증된 옵션이 이미 적혀 있으니 그대로 가져다 쓰면 된다.

| 서버 | 실행 명령 (해당 디렉토리 안에서 실행) |
|---|---|
| echoServer | `go run . -c_IsTcp4Addr=true -c_BindAddress=127.0.0.1:11021 -c_MaxSessionCount=200 -c_MaxPacketSize=1024` |
| chatServer | `go run . -c_IsTcp4Addr=true -c_BindAddress=127.0.0.1:11021 -c_MaxSessionCount=200 -c_MaxPacketSize=1024` |
| chatServer_msgpack | `go run . -c_IsTcp4Addr=true -c_BindAddress=127.0.0.1:11021 -c_MaxSessionCount=200 -c_MaxPacketSize=1024` |
| baccaratServer | `go run . -c_IsTcp4Addr=true -c_BindAddress=127.0.0.1:11021 -c_MaxSessionCount=200 -c_MaxPacketSize=1024` |

전부 기본적으로 `127.0.0.1:11021`(내 컴퓨터의 11021번 포트)에서 접속을 기다린다. 서버를 동시에 두 개 이상 띄워보고 싶다면 `-c_BindAddress`의 포트 번호를 서로 다르게 주면 된다(예: 11021, 11022).

참고로 `chatServer`/`chatServer_msgpack`/`baccaratServer`는 방(room) 관련 설정(방 개수, 방 하나에 들어갈 수 있는 최대 인원 등)이 커맨드라인 옵션이 아니라 `main.go` 안에 **직접 값이 박혀 있다**(`RoomMaxCount=1000, RoomStartNum=0, RoomMaxUserCount=4`). 즉 방 번호는 0번부터 999번까지 쓸 수 있고, 방 하나에는 최대 4명까지 들어갈 수 있다는 뜻이다. 다른 값으로 테스트해보고 싶다면 각 서버의 `main.go`에서 이 숫자를 직접 수정하고 다시 빌드하면 된다.

`go run .` 대신 `go build`로 실행 파일을 만들어 둘 수도 있다. 실행 파일 이름은 디렉토리 이름을 따라 자동으로 정해진다(`echoServer` 디렉토리에서 빌드하면 `echoServer.exe`가 만들어짐). `bin` 디렉토리의 `run_xxx.bat` 파일은 바로 이렇게 만든 `.exe`를 실행하는 용도이므로, 빌드한 `.exe`를 `bin` 디렉토리로 옮기면 그 배치 파일을 그대로 쓸 수 있다.

### 방법 2) GoLand에서 실행

GoLand로 서버 디렉토리(예: `echoServer`)를 프로젝트로 연 뒤, `main.go`를 실행하는 Run Configuration을 만들고 **Program arguments**에 위 표의 플래그들(`-c_IsTcp4Addr=true -c_BindAddress=...` 이하)을 그대로 입력하면 터미널로 실행한 것과 동일하게 동작한다. 디버깅(중단점 걸기 등)이 필요하면 이 방법을 쓰자. 예를 들어 `distributePacket.go`의 패킷 분기 코드에 중단점을 걸어두고 클라이언트에서 로그인을 시도해 보면, 패킷 하나가 서버 안에서 어떻게 처리되는지 한 줄씩 눈으로 볼 수 있다.


## 테스트 클라이언트 사용법

서버가 잘 만들어졌는지 눈으로 확인해 보려면 이 저장소에 포함된 C# GUI 클라이언트를 쓰면 된다. 텍스트 기반 도구(telnet 등)로는 테스트할 수 없다 — 패킷이 사람이 읽을 수 있는 텍스트가 아니라 [패킷 헤더](#패킷-헤더)에서 설명한 바이너리 포맷이기 때문이다.

1. `csharp_test_client/csharp_test_client.sln`을 Visual Studio로 연다. (`chatServer_msgpack`을 테스트할 때는 대신 `csharp_test_client_msgpack/csharp_test_client_msgpack.sln`을 연다.)
2. 빌드 후 실행한다(F5). WinForms 창이 뜬다.
3. IP 입력란은 기본값이 `0.0.0.0`이므로, "localhost" 체크박스를 켜거나 직접 `127.0.0.1`을 입력한다. Port는 기본값 `11021`을 서버와 동일하게 맞춘다(서버를 다른 포트로 띄웠다면 그 포트로 맞춘다).
4. **접속하기** 버튼을 눌러 서버에 연결한다. 로그 창에 접속 성공 메시지가 뜨면 성공이다. 아무 반응이 없거나 바로 끊긴다면 [문제 해결](#자주-겪는-문제) 절을 참고하자.
5. 서버별로 이어서 테스트할 기능이 다르다.
    - **echoServer**: "echo 보내기" 버튼을 누르면 보낸 내용이 그대로 되돌아오는 것을 로그에서 확인할 수 있다. 로그인/방 개념이 없으므로 이게 전부다.
    - **chatServer / baccaratServer(그리고 나중에 chatServer2를 직접 고쳐서 띄운다면 그것도)**: 아래 순서로 진행한다.
        1. UserID/PW 입력란을 채우고 **Login** 버튼을 누른다. (UserID는 빈 값이면 안 되고, DB 연동이 없는 실습 코드라 비밀번호는 아무 값이나 검사 없이 통과된다. 대신 **같은 UserID로 동시에 두 번 로그인하는 것은 막혀 있다** — 클라이언트 창을 여러 개 띄워 테스트할 때는 창마다 UserID를 다르게 주자.)
        2. 방 번호(0~999 사이 숫자, [위 실행 방법](#방법-1-터미널에서-바로-실행-가장-간단함) 절 참고)를 입력하고 **방 입장** 버튼을 누른다.
        3. 채팅 입력란을 채우고 **chat** 버튼을 누른다.
        4. 클라이언트 창을 두 개 띄워서(각각 다른 UserID로 로그인) 같은 방 번호에 입장시키면, 한쪽에서 보낸 채팅이 다른 쪽 로그 창에도 실시간으로 나타나는 것을 볼 수 있다. 이게 이 실습에서 가장 눈으로 확인하기 재밌는 부분이다.
    - **baccaratServer**: 위 채팅/방 기능까지는 이 클라이언트로 테스트할 수 있지만, 배팅 등 바카라 게임 자체를 조작하는 UI는 클라이언트에 없다(직접 추가해야 한다). 게임 진행 흐름은 `baccaratServer/docs/*.puml`(PlantUML 시퀀스 다이어그램 — VS Code의 PlantUML 확장 등으로 열어보면 그림으로 볼 수 있다)을 참고하자.
    - **chatServer_msgpack**: 같은 순서로 `csharp_test_client_msgpack`을 사용한다.


## 자주 겪는 문제

- **서버를 켰는데 클라이언트가 접속이 안 된다 / 바로 끊긴다**
    - `-c_MaxSessionCount` 플래그를 빼먹지 않았는지 확인한다(위 [주의] 참고 — 0으로 초기화되면 아무도 못 들어온다).
    - 서버와 클라이언트의 IP/Port가 정확히 같은지 확인한다(서버는 `127.0.0.1:11021`인데 클라이언트가 `0.0.0.0:11021`로 접속을 시도하고 있지는 않은지).
- **"주소가 이미 사용 중입니다(address already in use)" 같은 에러가 뜬다**
    - 같은 포트로 이전에 띄운 서버 프로세스가 아직 떠 있는 경우다. 터미널을 닫았다고 프로세스가 항상 같이 죽는 건 아니다. 작업 관리자(Windows) 등에서 `echoServer.exe`/`chatServer.exe` 같은 프로세스가 남아있는지 확인해서 종료하거나, `-c_BindAddress`의 포트 번호를 바꿔서 다시 실행한다.
- **로그인 버튼을 눌렀는데 실패한다**
    - UserID 입력란이 비어 있지 않은지 확인한다.
    - 같은 UserID로 이미 다른 클라이언트가 로그인해 있지는 않은지 확인한다(중복 로그인은 거부된다). 클라이언트 창마다 다른 UserID를 쓰자.
- **방 입장이 실패한다**
    - 방 번호가 유효한 범위(0~999, chatServer 계열 기본값 기준)인지 확인한다.
    - 방 하나에는 최대 4명까지만 들어갈 수 있다(기본값 기준). 같은 방에 5번째로 들어가려 하면 실패한다.
    - 로그인을 먼저 하지 않은 상태에서는 방에 입장할 수 없다.
- **`go run .`을 실행했더니 `go: downloading ...` 메시지만 계속 나온다**
    - 처음 빌드할 때 필요한 의존 라이브러리를 인터넷에서 내려받는 중이라 정상이다. 인터넷 연결을 확인하고 잠시 기다리면 된다. 한 번 받아두면 다음부터는 바로 실행된다.
    - `gohipernetFake`를 먼저 한 번 빌드해 두면(`cd gohipernetFake && go build ./...`) 이후 각 서버를 빌드할 때 참고하는 로컬 모듈이 준비되어 있어 도움이 된다.
    - `chatServer2`는 이 방법으로도 실행할 수 없다 — 코드 자체가 아직 빌드되지 않는 상태이기 때문이다. [해당 절](#chatserver2) 참고.

## chatServer

## chatServer2
- 디렉토리: chatServer2
- 방 개념의 채팅 서버
- 패킷 요청 처리를 N개의 고루틴(스레드)에서 한다.
    - 패킷 처리를 멀티 고루틴에서 하므로 공유 객체 동기화를 조심해야 한다.
- chatServer의 코드와 겹치는 부분이 많으므로 chatServer에 대한 이해가 꼭 필요하다
- 무엇을 배우는가: 접속자가 많아졌을 때 패킷 처리를 어떻게 여러 고루틴에 나눠서 병렬로 처리할지, 그리고 그 과정에서 여러 고루틴이 같은 데이터(세션, 방 상태)를 동시에 건드리지 않도록 어떻게 조심하는지(동기화). chatServer와 파일을 나란히 비교해 보면 "무엇이 병렬화 때문에 달라졌는지"가 잘 보인다.

> **현재 이 서버는 빌드되지 않는다.** `NTELIB_LOG_INFO`, `NTELIB_LOG_ERROR`, `NetLib_IsRunningServer`, `NetLib_GetCurrnetUnixTime` 등 여러 심볼이 코드 곳곳에서 쓰이지만 이 저장소 어디에도 정의되어 있지 않다. 그래서 위 [실행 방법](#go-서버를-빌드하고-실행하는-방법)으로 바로 실행할 수 없다. 코드를 읽으면서 "멀티 고루틴으로 어떻게 구조를 나눴는가"를 학습하는 용도로는 그대로 쓸 수 있지만, 직접 실행해 보려면 먼저 이 심볼들을 채워 넣어야 한다(예: 어딘가에 로그를 출력하는 함수와, 서버 실행 상태를 나타내는 함수를 직접 정의해서 채워 넣는 식). 이 자체를 하나의 작은 실습 과제로 삼아도 좋다.

## msgpack을 사용한 chatServer	
- 디렉토리: chatServer_msgpack
- 클라이언트 디렉토리: csharp_test_client_msgpack	
- 서버와 클라이언트가 네트워크로 주고 받는 패킷 데이터 포맷을 msgpack을 사용한다.
    - [Go](https://github.com/vmihailenco/msgpack )
	- [C#](https://github.com/ymofen/SimpleMsgPack.Net  ) 
	    - golang 라이브러리와 데이터 포맷이 일치하지 않는 부분이 있어서 코드를 수정하였음.
		- thirdparty/SimpleMsgPack.Net  디렉토리에 코드가 있다/
- 무엇을 배우는가: `chatServer`가 패킷 보디를 직접 손으로 바이트로 조립/해체하는 것과 달리, `chatServer_msgpack`은 이 작업을 msgpack이라는 범용 직렬화 라이브러리에 맡긴다. `protocol/packet.go`를 chatServer와 나란히 비교해 보면, 직접 만든 프로토콜과 범용 직렬화 라이브러리를 쓰는 방식의 장단점을 체감할 수 있다.
- 실행: [위 표](#방법-1-터미널에서-바로-실행-가장-간단함) 참고. 테스트는 `csharp_test_client_msgpack`으로 한다.
